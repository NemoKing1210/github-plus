# Security Policy

GitHub Plus is a userscript that runs inside `github.com` and `gist.github.com`
with the privileges of the visitor's own session. It is not affiliated with
GitHub, Inc. This page explains how to report a security problem and what the
project treats as in scope.

## Supported versions

Only the newest release on `main` is supported. The script auto-updates from
`main` through `@updateURL` / `@downloadURL`, so fixes ship in the next release
and there are no maintenance branches for older versions. If you are running an
older build, update first and check whether the issue still reproduces.

## Reporting a vulnerability

Please do **not** open a public issue for a security problem.

1. Use GitHub's private vulnerability reporting: open the repository's
   **Security** tab and choose **Report a vulnerability**. The report, the
   discussion and the fix stay private until an advisory is published.
2. If that form is unavailable, open a minimal public issue saying only that
   you have a security report and asking for a private channel — no details, no
   proof of concept, no affected URLs.

Useful in the report:

- the script version and userscript manager (Tampermonkey, Violentmonkey,
  ScriptCat, …) plus the browser;
- the page or page type where it reproduces (repository README, issue, pull
  request, gist, …);
- step-by-step reproduction and, where possible, a minimal proof of concept;
- the impact you expect — what an attacker gains that they did not have before.

## What to expect

- Acknowledgement of the report within **7 days**.
- An initial assessment within **30 days**, including whether it is in scope
  and a rough timeline for a fix.
- A fix released as the next version, with a `CHANGELOG.md` entry that describes
  the impact without publishing an exploit.
- Credit in the advisory and the changelog unless you ask to stay anonymous.

There is no bug bounty. This is a small volunteer project; the timelines above
are best effort, not a contract.

## Scope

In scope — problems in this project's own code or build:

- **Injection into injected UI.** Untrusted page content (markdown image URLs,
  alt text, titles, file and folder names) reaching the settings panel, viewer,
  toasts or file icons in a way that executes script, injects markup or escapes
  the `gp-` namespace.
- **Data exposure.** Reading, storing or transmitting anything beyond
  `gp_settings_v1` in GM storage; any network request not already made by
  GitHub in the same context. The script currently makes no cross-origin
  requests.
- **Privilege or permission creep.** Metadata or code that adds GM grants,
  `@connect` hosts or `@match` entries beyond what a feature actually needs.
- **Supply chain.** A malicious or compromised dependency, icon source or
  generated artifact that changes what the published `.user.js` does.
- **Update integrity.** A flaw in the build or release flow that lets a
  non-maintainer change the artifact served from `main`.

Out of scope:

- Vulnerabilities in GitHub itself — report those to
  [GitHub's Bug Bounty program](https://bounty.github.com/).
- Vulnerabilities in a userscript manager, browser or extension — report them
  upstream.
- Attacks that require an already-compromised browser profile, extension,
  operating system account or physical access.
- Self-XSS and cases where the victim is talked into pasting code or settings
  into the console or the import field themselves.
- A visitor editing their own `gp_settings_v1` data; it only affects their own
  browser.
- Bug reports without a security impact (broken layout, missing icon, gallery
  not opening) — use the regular issue tracker.
- Dependency advisories with no reachable path in the shipped bundle. They are
  still welcome and will be triaged, but are not treated as vulnerabilities of
  this project on their own.

## How the script is built to stay safe

These properties are part of the security posture; a change that breaks one of
them is a bug worth reporting:

- No analytics, telemetry or remote configuration.
- No cross-origin requests and no declared `@connect` hosts.
- Only `gp_settings_v1` is stored, through the manager's GM storage, wrapped so
  a sandbox without storage degrades instead of crashing the page.
- Injected elements live under `gp-` ids and classes and are excluded from the
  gallery's own click handling, so page content can never drive our UI.
- Release artifacts are generated by `npm run build` and verified byte for byte
  by `npm run verify:artifacts` in CI before they reach `main`.
