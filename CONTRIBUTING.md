# Contributing to GitHub Plus

Thanks for helping. GitHub Plus is a vanilla-JS userscript built with Vite;
read this before opening an issue or a pull request. Day-to-day build, test
and release steps live in [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Ground rules

- One issue or pull request per topic. Unrelated cleanups and refactors belong
  in their own pull request.
- This project is **not affiliated with GitHub, Inc.** Do not add copy,
  metadata or chrome that implies otherwise.
- By contributing you agree your work is licensed under the repository's MIT
  license.
- Be kind and stay on topic in issues and reviews.

## Prerequisites

- Node.js 22 (per `.nvmrc`) and npm.
- A userscript manager for testing: Violentmonkey (recommended — it can track a
  local file) or Tampermonkey.

## Setup

```bash
git clone https://github.com/NemoKing1210/github-plus.git
cd github-plus
npm install
npm run ci   # build + verify artifacts; must pass before you start
```

Installing the script for manual testing is covered in
[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md#local-testing).

## What to edit

- Source lives under `src/`; styles are plain CSS in `src/styles/`.
- `github-plus.user.js`, `github-plus.meta.js` and everything in `dist/` are
  build output. **Never hand-edit them.** Change `src/` (or `vite.config.js`
  for the userscript metadata) and run `npm run build`.

## Branching

Branch from `main` and prefix by intent: `feat/…`, `fix/…`, `docs/…`,
`chore/…`. Keep the branch focused on the one topic it is named for.

## Conventions

- Vanilla JavaScript ESM. No frameworks, no TypeScript, no added type layer.
- No new dependencies without discussing it in the issue first. `vite`,
  `vite-plugin-monkey` and `terser` are the whole toolchain.
- Respect the import direction `utils ← core ← gallery/features`. A module
  imports only from its own layer or a lower one: `utils` never imports `core`,
  `core` never imports `gallery` or `features`, and features do not reach into
  each other's internals. `src/main.js` is the composition root that wires the
  layers together (see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)).
- Prefix everything we inject with `gp-`: classes, injected element ids and our
  data attributes. Never restyle a GitHub class we do not own.
- English everywhere — code, identifiers, comments, commit messages and docs.
  The only non-English content is the string values in
  `src/i18n/locales/*.js` and the localized `@name` / `@description` entries in
  `vite.config.js`.
- Keep the userscript header minimal: `@match` and the GM grants are added only
  when a feature actually needs them, never "just in case".

## Localization

UI strings live in `src/i18n/locales/*.js`, one file per locale — ten in total
(`en`, `ru`, `de`, `es`, `fr`, `pt-BR`, `zh-CN`, `ja`, `ko`, `pl`). Every new
user-facing string must be added to **all ten files with identical key order**.
The English file is the reference; a machine-translated first pass is
acceptable if the pull request says so. If the change alters what the script
does, update the localized `@name` / `@description` metadata in
`vite.config.js` as well.

## Versioning and changelog

- Version numbers follow SemVer; `package.json` is the source of truth.
- A user-visible change includes a `CHANGELOG.md` entry under
  `## [Unreleased]` (Keep a Changelog format: `Added` / `Changed` / `Fixed`).
- Run `npm run build` after a version bump so both root artifacts carry the new
  version.
- Releases, tags and version bumps are handled by maintainers.

## Testing checklist

- [ ] `npm run ci` passes (`build` + `verify:artifacts`).
- [ ] The root `.user.js` / `.meta.js` were regenerated by the build, not kept
      stale.
- [ ] The change was tried on live `github.com` pages, in both placements of
      the settings entry where relevant.
- [ ] New strings exist in all ten locales with identical key order.
- [ ] No new console errors, and no new `GP-####` codes.

## Pull request process

1. Fork the repository and branch from `main` (see **Branching**).
2. Keep the pull request focused; drive-by refactors will be asked to split out.
3. Work the testing checklist and state in the description what you tested and
   on which pages.
4. Make sure CI is green before asking for review.
